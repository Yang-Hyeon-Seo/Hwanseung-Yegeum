# 환승 예금(Hwanseung-Yegeum)

## 📝 프로젝트 소개
"지금 예금을 깨고 저 예금으로 갈아타는 게 이득일까?"
**환승 예금**는 사용자가 기존 예금을 중도 해지하고 새로운 예금 상품으로 갈아탈 때의 유불리를 비교 분석해 주는 **금융 시뮬레이션 웹 서비스**입니다. 이를 통해 직관적이고 합리적인 금융 의사결정을 돕습니다.

## 💡 기술적 주안점 (Technical Highlights)

이 프로젝트는 금융 서비스의 생명인 계산의 무결성(Integrity)을 보장하기 위해 백엔드에 다음과 같은 핵심 로직을 설계했습니다.

1. **정확한 이자 계산**
  * 이자 계산 방법(`원금 * 이자율 * 실제 일자 / 365`)를 통해 이자 계산 로직을 구현했습니다.
  * 실제 예적금 만기 예상 조회를 통해 계산의 정확성을 높였습니다
   * 세전 이자 산출부터 최종 세후 이자 도출까지, 연산이 이루어지는 각 단계마다 독립적인 절사(Truncation) 과정을 거치도록 설계하여 실제 은행 결과값과 최대한 유사하게 진행하고자 했습니다.
   * 은행마다 약관의 차이가 존재할 것이기 때문에 100% 정확한 결과를 보장하지는 못하지만, 이는 10원 미만의 작은 단위일 것이라 예상합니다.
2. **부동소수점(Float) 오차 원천 차단**
   * Python의 기본 `float` 연산 시 발생하는 이진법 근사치 오류를 막기 위해, 금액 및 이율 등 모든 실수 연산에 `Decimal` 객체를 도입했습니다.
   * 외부 데이터 파싱 시 `Decimal(str(value))` 형태로 변환하여 미세한 소수점 유입을 방지했습니다.

3. **은행 실무 수준의 단수 처리 (Quantize & Rounding)**
   * 단순 `round()` 함수 대신 `Decimal.quantize()`를 활용했습니다.
   * 세전 이자와 세금(15.4%) 계산 시 실무 은행과 동일하게 **원 단위 미만 절사(`ROUND_DOWN`)** 규칙을 일관되게 적용하여 1원의 오차까지 제어합니다.

- 문제상황

    ```
    초기 로직 구현 후, 백엔드에서 계산한 이자 결과(예: 31,454원)가 실제 은행 앱에서 조회한 만기 이자(예: 30,530원)와 크게 차이나는 문제가 발생하여 이를 금융권 표준 로직에 맞게 교정하는 과정을 거침.
    ```
  - 이자 계산 로직은 비슷한데 함수가 여러개인 문제 발생
- 문제 해결 방법
  - 다음의 방법을 통해 문제를 해결함
  - 문제 해결 과정에서 실제 금융 상품 가입 및 기존 상품 등을 활용하여 정확성 확인

## 🛑 트러블 슈팅 1. 이자 및 세금 계산 시 발생하는 소수점 오차
### Problem
* 단순 곱셈 산식(`원금 * 연이율 * (총일수 / 365)`)을 사용하고 반올림(`ROUND_HALF_UP`)을 적용했더니 실제 은행 계산 결과보다 금액이 크게 나옴.
* 세후 이자를 구할 때 `이자 * (1 - 세율)` 방식을 사용함.

### Cause
1. **절사(Truncation) 원칙 누락:** 국내 은행의 예적금 계산은 소수점이 발생할 때마다 '원 단위 미만 절사'를 수행함. 반올림을 쓰면 실제보다 금액이 커짐.
2. **세금 계산의 순서:** 국가에 납부하는 세금 자체도 원 단위 미만을 버림. 따라서 세전 이자에서 세금 비율을 차감하는 방식이 아니라, '세금을 먼저 구해서 절사'한 뒤 세전 이자에서 빼야 함.

### Solution
* `decimal` 라이브러리를 도입하여 부동소수점 오차를 제어함.
* 계산 단계를 분리하고, 각 단계가 끝날 때마다 절사(버림)를 수행하는 `f_quantize` 함수를 적용함.
* 세금 계산 방식을 `이자 * (1 - 세율)`에서 `이자 - 절사(이자 * 세율)`로 변경함.

## 🛑 트러블 슈팅 2. "Banker's Rounding"에 대한 오해와 `ROUND_DOWN`
### Problem
* 검색을 통해 금융권에서는 오사오입 방식인 `ROUND_HALF_EVEN`(Banker's Rounding)을 쓴다는 정보를 얻어 적용해 보았으나, 실제 새마을금고 데이터와 10원 단위의 오차가 발생함.

### Cause
* `ROUND_HALF_EVEN`은 서구권 금융, 통계, 혹은 환율 등 대규모 회계 결산 시 오차를 줄이기 위해 사용되는 방식임.
* **국내 예적금 이자 및 소득세법**의 기본 원칙은 "원 단위 미만은 계산하지 않는다(절사)"임. 

### Solution
* `ROUND_HALF_EVEN` 대신 **`ROUND_DOWN`(내림/버림)** 옵션을 채택하여 실제 금융권 데이터와 계산 결과를 일치시킴.

## 🛑 트러블 슈팅 3. 10원 단위 절사를 위한 `Decimal` 표현식 오류
### Problem
* 세전 이자의 일의 자리가 0이나 5로 불규칙하게 떨어지는 것을 막고, 보수적으로 10원 단위로 절사하기 위해 `Decimal('-1')`을 인자로 넣었으나 원하는 대로 절사되지 않음.
* 이를 해결하기 위해 `Decimal('10')`을 넣었으나 1원 단위로 절사됨

### Cause
* 파이썬 `decimal.quantize()` 메서드에서 10 단위로 절사(일의 자리 버림)를 명확히 지시하려면 `1E1`를 사용해야 함.

### Solution
* `f_quantize` 함수 내의 인자를 `Decimal('1E1')`로 명확히 수정하여 10원 단위 절사를 완벽히 구현함.

## 🛑 트러블 슈팅 4. 윤년(Leap Year) 처리로 인한 일할 계산 오류
### Problem
- 가입 연도에 윤년이 포함되었는지(calendar.isleap) 확인하여 분모(year)를 366으로 동적 할당함. 그러나 은행 결과와 미세한 금액 오차가 발생함.

### Cause
- 대부분의 국내 시중은행 및 제2금융권은 상품 약관에 따라 윤년 여부와 상관없이 1년을 365일로 고정하여 일할 계산(Day Count Convention)을 수행함. 분모가 366이 되면 이자가 실제보다 적게 계산됨.

### Solution
- 윤년 체크 로직을 제거하고, year = Decimal('365')로 하드코딩하여 금융권 표준에 맞춤.
